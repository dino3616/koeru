# KOERU の正本（FSL の外側）

**FSL が扱わない情報はここが正本。** 形式的な契約（状態・遷移・不変条件・受入・禁止）は [specs/](../specs/) にある。

| 何の正本か | 場所 | ID |
|---|---|---|
| 満たさなければ製品が成立しない条件 | `requirements/{領域}.toml` | `TR-{領域}-{番号}` |
| 何を選び、なぜ選び、何が起きたら覆すか | `decisions/DEC-*.toml` | `DEC-{領域}-{番号}` |
| まだ決まっていないこと | `questions/Q-*.toml` | `Q-{領域}-{番号}` |
| 判断の根拠。調査資料、実測 | `evidence/EVID-*.toml` | `EVID-{種別}-{番号}` |
| 部品台帳。ライセンス監査の面 | `evidence/ledger-{領域}.toml` | `CMP-{領域}-{番号}` |
| 上限と配分。合計を検査する | `budgets/BUDGET-*.toml` | `BUDGET-{種別}-{番号}` |
| 領域ごとの性能目標。上限は無い | `budgets/{領域}.toml` | `TGT-{領域}-{番号}` |
| **代表プロジェクトの規模。予算はここから導く** | `budgets/SCALE-*.toml` | `SCALE-{種別}-{番号}` |
| リリース対象 | `profiles/PROFILE-*.toml` | `PROFILE-{名前}` |

**すべての項目が ID を持ち、ID で引ける。** 1件1ファイルのものも、収集ファイルの中の1件も同じ。
**引けないものは参照できず、参照できないものは検査できない。** 名前で参照すると、改名で黙って古くなる。

## ファイルは自分の形を名乗る

**すべての meta ファイルは先頭で `schema` を宣言する。** 名乗らないファイルは検査で落ちる。

| schema | 置き場所 | 形 |
|---|---|---|
| `requirement-set` | `requirements/` | `[[requirement]]` の配列 |
| `decision` | `decisions/` | 1件1ファイル。`DEC-*` |
| `question` | `questions/` | 1件1ファイル。`Q-*` |
| `evidence` | `evidence/` | 1件1ファイル。`EVID-*` |
| `component-ledger` | `evidence/` | `[[component]]` の配列 |
| `budget` | `budgets/` | 1件1ファイル。`BUDGET-*`。上限と配分を持つ |
| `target-set` | `budgets/` | `[[target]]` の配列。上限は無い |
| `scale-reference` | `budgets/` | 1件1ファイル。`SCALE-*`。基点と `[[derived]]` の導出式を持つ |
| `profile` | `profiles/` | 1件1ファイル。`PROFILE-*` |

**1つのディレクトリに2つの形が入るのは、それが同じ種類のものだから。** 予算と目標値はどちらも
「FSL が表現できない数値」で、検査できることだけが違う。台帳と Evidence はどちらも「判断の根拠」。

**形を名乗らせるのは、黙って0件になる経路を塞ぐため。** ディレクトリの中身から形を推測すると、
`[[component]]` を `[[componnet]]` と書いたファイルが「収集ファイルではない」とみなされ、
**その分だけ件数が減ったまま検査を通ってしまう。** 261件あると言っていたのに本文が118件しか
なかったのと同じ故障で、次の6つはいずれも検査が落とす。

- `schema` を書き忘れる / 知らない `schema` を書く / 置き場所と形が合わない
- **件数を散文に書く。** 数は `cargo xtask check-meta` が数える。書くと片方だけが古くなる
- 部品の採否を「採用」「不適」に決めたのに `decided_by` を書かない（理由と撤回条件が残らない）
- `id` が無い（1件1ファイルでも、収集ファイルの1件でも）
- `id` の接頭辞が形と合わない / `id` が重複する
- 収集キーを打ち間違える（**一部だけ間違えた場合も含む**）
- 収集ファイルの項目が0件
- 存在しない ID を参照する

**予算に2つの形があるのは、検査できることが違うから。** `BUDGET-*` は上限と配分を持ち、
**合計が上限を超えていないかを算術で検査する。** 領域ごとの目標値には上限が無く、合計に意味が無い。

**部品台帳は採否を持たない。** ライセンス監査の面として name / purpose / license / status を持ち、
**なぜその採否なのかは `decided_by` が指す判断記録が持つ。** `decided_by` の無い `採用` / `不適` は、
まだ判断記録になっていない採否（→ Q-ALL-004）。

## 確度の読み方

| タグ | 意味 |
|---|---|
| **[Fact]** | 一次情報（ソース実物、ライセンス原文、実測）で確認済み |
| **[Assumption]** | 妥当と考えるが検証していない。外れたら要件が動く |
| **[Unknown]** | 分かっていない。分かっていないことを明示するために書く |
| **[Risk]** | 成立しなかった場合に何が壊れるか |

## 規律

**同じ命題を2箇所に書かない。** ある要件が FSL で形式化されているなら、その要件の `formalized_as` に FSL の ID を書き、契約そのものは FSL が持つ。**食い違ったら FSL 側が正。**

**手書きの文書（`docs/`）に規範的な内容を書かない。** 背景・物語・意図・調査の説明だけを持たせ、規範は ID で参照する。

> 悪い例: `F0 推定は SwiftF0 を採用する。`
> 良い例: `F0 推定の方針は DEC-SYN-001 を参照。`

**論点（`questions/`）では判断はしない。選択肢と帰結だけを並べる。** 決めたら `decisions/` へ移し、論点は閉じる。

**確度は下げる方向にしか動かない。** [Fact] と書いたものは一次情報で確認済みという意味で、推測を [Fact] にしない。

## 検査

```bash
cargo xtask check-meta       # 必須項目と、参照先 ID の実在
cargo xtask check-budgets    # 配分の合計が上限を超えていないか
cargo xtask check-profile ID # 未決の論点がリリースを塞いでいないか
```

`check-meta` は、要件が参照する `TR-*` が登録簿に実在すること、`formalized_as` が FSL に実在すること、`depends_on` が解決することを検査する。**本文の無い ID を参照する状態には戻れない。**
