# KOERU の正本（FSL の外側）

**FSL が扱わない情報はここが正本。** 形式的な契約（状態・遷移・不変条件・受入・禁止）は [specs/](../specs/) にある。

| ディレクトリ | 何の正本か | ID |
|---|---|---|
| `requirements/` | 満たさなければ製品が成立しない条件 | `TR-{領域}-{番号}` |
| `decisions/` | 何を選び、なぜ選び、何が起きたら覆すか | `DEC-{領域}-{番号}` |
| `questions/` | まだ決まっていないこと。何が困るか、どう閉じるか | `Q-{領域}-{番号}` |
| `evidence/` | 判断の根拠。調査資料、ライセンス、実測 | `EVID-{種別}-{番号}` |
| `budgets/` | 上限と配分。合計が上限を超えていないかを検査する | `BUDGET-{種別}-{番号}` |
| `targets/` | 領域ごとの性能目標値 | ID を持たない |
| `technologies/` | 候補技術とライセンス、採否 | ID を持たない |
| `profiles/` | リリース対象。未決の論点が塞いでいれば落とす | `PROFILE-{名前}` |

## 確度の読み方

| タグ | 意味 |
|---|---|
| **[Fact]** | 一次情報（ソース実物、ライセンス原文、実測）で確認済み |
| **[Assumption]** | 妥当と考えるが検証していない。外れたら要件が動く |
| **[Unknown]** | 分かっていない。分かっていないことを明示するために書く |
| **[Risk]** | 成立しなかった場合に何が壊れるか |

## 規律

**同じ命題を2箇所に書かない。** ある要件が FSL で形式化されているなら、その要件の `formalized_as` に FSL の ID を書き、契約そのものは FSL が持つ。**食い違ったら FSL 側が正。**

**手書きの文書（`docs/`）に規範的な内容を書かない。** 背景・物語・意図・調査の説明だけを持たせ、規範は ID で参照する。

> 悪い例: `F0 推定は SwiftF0 を採用する。`
> 良い例: `F0 推定の方針は DEC-SYN-001 を参照。`

**論点（`questions/`）では判断はしない。選択肢と帰結だけを並べる。** 決めたら `decisions/` へ移し、論点は閉じる。

**確度は下げる方向にしか動かない。** [Fact] と書いたものは一次情報で確認済みという意味で、推測を [Fact] にしない。

## 検査

```bash
cargo xtask check-meta       # 必須項目と、参照先 ID の実在
cargo xtask check-budgets    # 配分の合計が上限を超えていないか
cargo xtask check-profile ID # 未決の論点がリリースを塞いでいないか
```

`check-meta` は、要件が参照する `TR-*` が登録簿に実在すること、`formalized_as` が FSL に実在すること、`depends_on` が解決することを検査する。**本文の無い ID を参照する状態には戻れない。**
