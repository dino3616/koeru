# 制作者が書き残しているもの

`docs/design/redesign-plan.md` の Phase 1 のうち、聞き取り無しでも取れる事実の3つめ。拾った内容そのものは `EVID-UX-003` が持つ。ここは読みどころを書く。

聞き取りではない。 こちらから質問していないので、聞きたいことが書かれている保証は無く、書く気になった人だけが母集団になっている。それでも `docs/journey-map.md` の `※推測` より一段強い——推測ではなく、誰かが実際に書いた言葉なので。

## 読みどころ

### 教える側も用語を説明しきれていない

周波数表について「説明がわりとむずいので『謎の表』として覚えてね」と書いている入門記事がある。何であるかを説明せずに、手順として通過させている。

`docs/journey-map.md` の【調べる】は「最初に出会うのが声ではなく用語になっている」と書いた。同じことが教える側でも起きていて、**説明を諦めた用語が手順の中に残っている。** 用語を出さないという方針は、初学者への配慮というより、誰も説明できていないものを画面から外すことに近い。

### 工程の分断は、記事の目次の形で見える

ある入門記事が挙げる工程は8つ。音源構成の検討、収録、原音設定、キャラクターイラスト、その他同梱物、利用規約、アップローダー、配布動画。使うソフトは OREMO・setParam・UTAU。

スマートフォン収録の記事はさらに1つ多い。周波数表を作るためだけに speedwagon が挟まる。KOERU は周波数表を録音の副産物として書き出すので、この工程はまるごと消える。

`docs/product-vision.md` が「4つ以上に分断された工程」と書いたものは、具体的なソフト名で数えられる。

### 読み上げの難しさは、手作業の量とは別の軸

CVVC と連続音について「読み上げむずすぎ」とし、「ささんすぃさすさすぃ」のような行を初心者が読むのは「まず不可能」と書いている記事がある。同じ記事が、行は「長ければ長いほど読み間違いが発生しやすく、結果的に収録時間が無駄に伸びるしイライラする」として8モーラを最適としている。

`docs/product-vision.md` は方式の選択肢を「手作業が必要かどうか」を主軸に見せると決めている。**読み上げの難しさは、その軸とは独立に効く。** 全自動で完結する方式を選んでも、行が読めなければ録音が進まない。

軸は1本のままにする。 吸収するのは提示の設計のほうで、扱いは `Q-REC-005`。単独音は `TR-RCL-03` の行の長さで既に対処されていて、破綻するのは CVVC と連続音の行の中身そのもの——M5 の領域になる。

### 失敗の発見が遅れることを、当たり前として書いている

「マイクの位置取りが悪くて全部録り直ししないといけない」「発音が間違ってて修正が効かない」が「当たり前にある」と書かれている。

`docs/usecase-map.md` は F04 の前提として「録音時の品質判定（音量不足、クリッピング、声質の変化）は今回の範囲外。失敗の発見は試唱まで遅れる」と置いている。この前提は、制作者が実際に踏んでいる場所と同じところに立っている。

これを受けて禁止を緩めるかを検討し、緩めないことにした（`DEC-REC-008`）。 技術的には判定できる——計測はすでに義務づけられていて、クリッピングの規則は要件の中に数式で書かれている。できないから出さないのではない。**割れた音や小さい音を特徴として使う制作者がいるかもしれないから、出さない。** 何が「不備」かを製品が決めない、という判断になっている。

### 原音設定のコストは、習熟後の数字で語られている

「原音設定は、ある程度習熟した後でも、連続音1音階あたり1〜2時間程度の作業時間が必要」と書いている記事がある。習熟前ではなく、習熟後。

自動原音設定が実用水準に届くかどうかは未決のままだが（`DEC-ALN-007`）、届いたときに消える時間の大きさは、この数字で見積もれる。
