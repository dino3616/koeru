# 既存ツールの情報構造

`docs/design/redesign-plan.md` の Phase 1 のうち、聞き取り無しでも取れる事実の1つめ。観察した内容そのものは `EVID-UX-002` が持つ。ここは読みどころと、KOERU の設計にとって何を意味するかを書く。

実機は動かしていない。 公開文書の記述だけから組み立てているので、現行版の画面がそのとおりである保証は無い。確度は Assumption。

## 読みどころ

### 録音の前に、利用者がファイルを組み立てる

OREMO は録音リストとガイド BGM と BGM 設定ファイルの3つを、RecStar は録音リストとコメントファイルとガイド BGM の3つを、それぞれ利用者が用意して読み込ませるところから始まる。どれも「どれを選ぶか」を判断できるだけの材料が、まだ手元に無い時点で求められる。

`docs/journey-map.md` の【調べる】で用語に当たって止まる経路は、ここに接続している。用語を覚えないと、読み込ませるファイルを選べない。

**KOERU が持ち込ませるものはゼロ。** 録音リストは内部生成する（`TR-RCL-02`）。Create before configure が実装として意味しているのは、この3ファイルを消すことだった。既存ツールとの差がいちばん構造的に出るのはこの一点で、リデザインで薄めてはいけない。

### 項目ごとの状態を持っているのは vLabeler だけ

vLabeler はエントリごとに Done・Star・Tag を持ち、ショートカット1打で切り替えられて、絞り込みの軸になる。ピン留めした一覧が常駐する。

OREMO と RecStar は「録れたかどうか」しか持たない。setParam と OpenUtau は項目ごとの状態を持たない。

KOERU の収録項目が持っているのは、採用テイクがあるかどうかと、テイクの世代だけ。「後で見直す」「ここは怪しい」を置く場所が無い。自動原音設定が確信度の低い箇所だけを人に確認させる設計（`UC-F04-02`）は、確認待ちという状態を項目が持てないと成立しない。**M6 で必要になる状態を、M2 の収録項目に載せられる形で先に設計しておく。** Phase 3 が M7 まで見る理由のひとつがこれ。

### 工程が変わるとアプリが変わる

録音は OREMO か RecStar、原音設定は setParam か vLabeler、歌わせるのは OpenUtau。工程間を渡るのはフォルダとファイルで、対象の同一性ではない。同じ音が同じものだと保証しているのはファイル名の一致だけ。

`docs/product-vision.md` が最優先で背負うと決めた痛みは、この分断そのもの。だから KOERU の OOUI は、3工程を横断して同じオブジェクトを指し続けられる骨格である必要がある。工程ごとに画面を分けてもよいが、オブジェクトを分けてはいけない。

### 俯瞰する面と、1件を詳しく見る面が分かれている

OpenUtau はトラック面とピアノロールをダブルクリックで行き来する。vLabeler はサンプルとエントリを別の軸で移動する。どちらも、全体を見る面と1件を扱う面が分かれている。

KOERU の現行も音源一覧と収録の2階層だが、下の階層に5種類のオブジェクトが同居していて、「1件を詳しく見る面」がどのオブジェクトのものなのかが決まっていない。テイクを詳しく見ているのか、収録項目を見ているのか、音源を見ているのか。

## Phase 3 へ持ち越すもの

- 収録項目が持つべき状態の一覧。少なくとも「確認待ち」を置ける形にする
- 俯瞰の面と詳細の面をどのオブジェクトで切るか
- 3工程を横断して同一性を保つオブジェクトはどれか
