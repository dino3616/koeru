## 2. Segmentation Axes（セグメンテーション軸）

### 軸1: 現在の代替手段
- **なぜ重要か**: 競合と乗り換えコストが決まる。「何もしていない人」と「既存ツールで回せている人」では説得の順序が真逆になる。
- **観測された値**: **[Fact]** OREMO 58.5% / RecStar 33.3%（全体 n=477）、新規層は RecStar 64.7% / OREMO 29.4%（n=51）。setParam 70.9% / vLabeler 24.7%。**[Fact]** 未経験者は「何もしていない」。**[Unknown]** ACE Studio など AI 歌声サービスへ流れた層の規模。
- **補足**: 利用率は重複利用を含むためシェアではない。

### 軸2: 熟練度（用語の理解）
- **なぜ重要か**: 既定値・用語の露出・上級モードの開き方を直接決める。JM の HMW 6（方式選択の既定）はこの軸への回答そのもの。
- **観測された値**: **[Fact]** UTAU 歴1年未満が約1/8、1-3年が約1/3。**[Assumption]** 用語の理解度は歴と相関するが、歴が長くても方式選択の判断は毎回やり直している（JM ハル）。

### 軸3: JTBD（何のために作るのか）
- **なぜ重要か**: 同じ「音源を作る」でも、完成の定義が違えばプロダクトの終点が変わる。
- **観測された値**: **[Assumption]** ①自分の声が歌うのを聴きたい ②キャラクターを作りたい ③他人に使ってほしい ④自分の曲を自分の声で歌わせたい。**[Unknown]** この4つの分布。調査は「作るか / 作らないか」しか聞いていない。

### 軸4: 声の公開・手渡しへの態度
- **なぜ重要か**: **ビジョンの Made to be shared が成立するかどうかがこの軸で決まる。** 手渡しを前提にすると、この軸の一方の極が構造的に排除される。
- **観測された値**: **[Fact]** 「恥ずかしい・自信がない」22.2%、「配布の知識・技術がない」27.0%（n=63）。**[Unknown]** 「配布したくない」と「配布の仕方が分からない」の切り分けができていない。**[Risk]** 前者が多数なら Made to be shared は入口を狭める。

### 軸5: 録音環境の制約
- **なぜ重要か**: 最大の障壁でありながら、Scope decisions で「今は背負わない」と決めた領域。どこまで妥協して成立させるかを決める。
- **観測された値**: **[Fact]** 「録音機材や場所がない」46.0%（n=63、最多）。**[Assumption]** イヤホンマイク・生活音あり・小声という条件が現実解（JM ミナ）。

### 軸6: 役割（作る側 / 歌わせる側）
- **なぜ重要か**: UTAU 文化は「作る人」と「使う人」が分かれていることで循環していた。KOERU が片側だけを持つと、手渡しの先が製品の外に出る。
- **観測された値**: **[Fact]** 制作経験者 79.5% は「両方やる人」が多数派であることを示唆する。**[Unknown]** 歌わせる専門の人が UTAU 人口のどれだけを占めるか（調査は UTAU ユーザー全体が母集団のため切り分け不能）。

### Counter-persona（ソラ）が置かれている理由

ミナとハルに共通する中核軸は **軸4「声を他者へ手渡す」** — ビジョンの Made to be shared そのもの。ソラはその**正反対の極**にいる。

- **設計判断が衝突する点**: 「歌えるようになった声を誰かに渡せる」導線が主要な達成感として設計されるほど、ソラは「ここは自分の場所ではない」と判断する
- **堅牢性のシグナル**: Create before configure（まず歌う）は、ソラにも同じだけ価値がある。**手渡しを外しても成立する部分**が KOERU の核にあることを示している
- **明示すべきトレードオフ**: **[Risk]** 「誰かに使われて、初めて完成する」を製品のコピーとして前面に出すと、ソラは録音を始める前に離脱する。思想を掲げることと、それを未完成の判定基準として見せることは別に設計できる

## 5. Human Decision Gates（人間が決めるべき論点）

### 論点 1: Primary をどのセグメントにするか

**問い**: 最初のプロトタイプを、S1（潜在制作者）と S2（現役制作者）のどちらに当てるか。

**選択肢**:
- **A: S1 を Primary** — メリット: 差分が最大（JM でミナは試唱フェーズに一度も到達していない）。PDF の「最初の検証対象は制作未経験者」と一致。デメリット: **[Unknown]** 規模が測れていない。募集経路も未確立で、そもそも12-20人集められるか不明
- **B: S2 を Primary** — メリット: **[Fact]** 477人という母集団があり、X 上でアクセスできる。検証コストが最も低い。デメリット: 既存ツールに最適化済みで、乗り換えの動機が弱い可能性。**[Risk]** 「便利だね」で終わり、移行しない
- **C: 両方を Primary のまま進める** — メリット: ビジョンの Who と一致。デメリット: 既定値の設計が両方に最適化できず、結果的にどちらにも刺さらない可能性

**現時点での情報**: **[Fact]** S2 の規模と接触可能性のみが確認済み。S1 は規模・接触経路ともに **[Unknown]**。

**判断のために必要な追加情報**: S1 に到達できる募集経路が実在するか（UTAU 圏外で「自分の声で歌わせたい」人をどこで見つけるか）。

**判断の保留がもたらすコスト**: 保留のままプロトを作ると、既定値（方式指定を開くか閉じるか、用語をどこまで出すか）が決まらず、着手できない。

**Agent の推奨**: **B で検証し、S1 の募集経路を並行して探す。これは推奨であり、決定は人間のもの。** 理由は、A の最大の不確実性が「プロダクトが刺さるか」ではなく「被験者を集められるか」であり、それは設計ではなく調達の問題だから。ただし **[Risk]** S2 だけで検証すると、S2 が既に用語を理解しているために「用語を隠す」価値を検証できない。

### 論点 2: Counter-persona（ソラ）をどこまで受け止めるか

**問い**: 「誰にも渡したくない」人を、設計上どう扱うか。

**選択肢**:
- **A: 明示的に切る** — メリット: Made to be shared の解像度が上がる。デメリット: **[Fact]** 恥ずかしさ22.2% の一部を入口で失う
- **B: 最低限を担保する** — 手渡しを既定にしつつ、非公開のまま完成できる状態を正規のルートとして残す。メリット: Create before configure の価値は全員に届く。デメリット: 「完成」の定義が2つになり、進捗表現が複雑になる
- **C: 両立を正面から設計する** — 公開・非公開を対等な完成形として扱う。メリット: 市場が広い。デメリット: ビジョンの中核が薄まる。「誰にでも刺さる」の罠

**現時点での情報**: **[Fact]** 恥ずかしさ22.2%、配布知識なし27.0%。**[Unknown]** この2つの重なりと、「渡したくない」と「渡し方が分からない」の比率。

**判断のために必要な追加情報**: 未経験者への追加調査で「完成したら公開したいか」を直接聞く。

**判断の保留がもたらすコスト**: オンボーディングのコピー（「誰かに使われて、初めて完成する」を出すか）が決まらない。

**Agent の推奨**: **B。これは推奨であり、決定は人間のもの。** 根拠は **[Assumption]** — 「渡したくない」の相当部分は「今は渡す自信がない」であり、時間とともに動く可能性がある。最初から締め出すと、後から戻ってこられない。

### 論点 3: S3（歌わせる側）を製品範囲に含めるか

**問い**: KOERU は「作る側の道具」で止まるのか、手渡しの先（配布と発見）まで持つのか。

**選択肢**:
- **A: 作る側に閉じる** — 配布パッケージ（ZIP）の生成まで。メリット: スコープが小さく、既存の配布文化を壊さない。デメリット: **[Risk]** 手渡しの先が製品の外にあるため、Made to be shared が思想止まりになる
- **B: 配布の場まで持つ** — メリット: 手渡しのループが製品内で閉じ、S3 が獲得経路になる。デメリット: 規約・権利・モデレーションを背負う。UTAU の分散型配布文化と衝突する可能性

**現時点での情報**: **[Fact]** 既存の配布は個人サイト・SNS・GAKUYA に分散。中央の配布所は存在しない。**[Unknown]** 制作者が中央集約を望むか。

**判断のために必要な追加情報**: 現役制作者に「配布先が KOERU 内にあったら使うか、自分のサイトを続けるか」を聞く。

**判断の保留がもたらすコスト**: **これは product-vision.md の Assumptions「手渡しの実装範囲」と同じ論点。** 保留の間、ビジョンの How it's different が検証不能なまま残る。

**依存関係**: **論点 2 を B/C にすると、論点 3 で「非公開の置き場」も必要になる。**

### 論点 4: 検証の順序

**問い**: JM のコアシーン候補のうち、どれを先に検証するか。

**選択肢**:
- **A: 候補2（方式非依存の中間表現）を技術検証から** — メリット: 失敗したら To-Be の後半とビジョンの差別化が崩れるので、早いほど安い。ユーザー募集が不要。デメリット: ユーザー側の学びがゼロ
- **B: 候補1（5分で歌う）をユーザープロトから** — メリット: 体験の核が検証できる。デメリット: 論点1 が未決だと被験者が決まらない
- **C: 並行** — メリット: 早い。デメリット: **[Assumption]** 現状のリソースで並行できるかは不明

**現時点での情報**: **[Risk]** 候補2 が成立しないと、HMW 6 に基づく To-Be の後半（【広げる】【方式を確定して書き出す】）が全て崩れる。

**判断のために必要な追加情報**: なし。A は今すぐ着手できる。

**判断の保留がもたらすコスト**: 論点1 の決着を待つ間、何も進まない。

**Agent の推奨**: **A を先に。これは推奨であり、決定は人間のもの。** 論点1 に依存しない唯一の検証であり、失敗時の影響が最も大きいため。

## 6. Next Action

この Stage 1 出力は「材料」です。次にやることは2つ。

1. **比較表（#3, #4）を見て、列・行を追加・修正してください**
   気になる軸が漏れていれば追加してください。特に **軸3（JTBD）の分布が全て [Unknown]** なので、直感で埋められる部分があれば書き換えてください。

2. **Human Decision Gates（#5）の4つの論点に答えてください**
   各論点に「A/B どちらか」「なぜ」「どんな前提が変わったら変えるか」を返してもらえれば、Primary 候補を確定 → Stage 2（深掘り + Validation Plan）に進みます。

**論点1 が決まれば論点4 の B が動き出し、論点2 が決まれば論点3 の範囲が絞れます。** まず論点1 から答えるのが効率的です。

判断に必要な追加情報があれば「Unknown のここを埋めたい」と言ってください。
