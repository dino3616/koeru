# 体制 — 画面刷新

このキャンバスの画面を、プロトタイプの画面と差し替えるときの体制。工程と判定は [delivery-phase-plan.md](delivery-phase-plan.md)、日付は GitHub のマイルストーンが持つ。差し替えが済んだら、この文書は消す。

- **範囲:** キャンバスの画面を、新しい IA と表層で作り直す。サブバンク（1つの音源の中で、枠ごとに方式・声色・音階を持つ）と、複数の配布物とその版は、ドメインから作る
- **Owner:** エンジニア A。範囲、判断記録、各関門の Go / No-Go を持つ
- **Support:** 置かない

## 層

| 層 | 誰 | 持つもの |
|---|---|---|
| Owner | エンジニア A | 範囲と切る線、判断記録（DEC / TR / SDL）、Rust と meta の PR の承認、main へのマージ、Go / No-Go |
| 実行: 重い機能とドメイン | エンジニア A | サブバンクの migration と Rust の口、枠ごとの方式、収録の組み立て、ピアノロールの範囲の操作。P1 では音高グラフ、配布の棚と版 |
| 実行: Issue プール | エンジニア B、エンジニア C（同列） | P6 の部品、シェル、重くない画面、story と axe。空いている Issue から優先度と画面の順位の順に取る。WIP は1人1本 |
| 実行: レビュー | エンジニア D | フロントの PR を、規約・lint の contract・a11y の観点で承認する |

B と C は `meta/` を書かない。読むのは自由。meta への書き込みが要る作業は A の Issue に寄せる。試験は既存の story と lib の unit 試験に足す。`meta/suites/` の登録は床の件数なので、それで書き換えずに済む。

## RACI

| 意思決定 | A | B / C | D |
|---|---|---|---|
| 範囲と切る線（P0 / P1 / P2、画面の順位、何を持ち越すか） | A | R | I |
| 表層トークン（書体は Canvas、色は Radix の段） | A | R | C |
| フロントの PR の受入（規約・a11y を満たすか） | C | R | A |
| Issue の取り方と着手順（優先度と順位の順、WIP 1） | A | R | I |
| 画面に実データが足りないときの扱い（席を置くか、Rust を足すか） | A | R | C |
| Go / No-Go と持ち越し | A | R | C |

A 決裁 / R 実行 / C 相談 / I 報告
