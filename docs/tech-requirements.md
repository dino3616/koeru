**判断が必要な論点は残っていない。** 当初の横断検証は10件の blocker を検出したが、8件は決定によって解消し、残る2件（B5 / B6）は解決方針まで定まった作業として「未解決の設計課題」に残る。いずれもメモリ予算の破綻に関するもので、実装着手前に数値を積み直す必要がある。解消した8件も、要件本文からの参照先として ID と経緯を残している。

## 実装方針の要約（確定している制約）

変更提案の対象外。この制約下で技術判断を行う。

| 制約 | 内容 |
|---|---|
| ライセンス | AGPL-3.0。OSS として公開し Issue / PR を受け付ける。DCO を導入 |
| 形態 | 単一のネイティブアプリケーション。PC 前提。**実装は Rust + Tauri** |
| 配布 | 直接ダウンロードを主経路。Microsoft Store は GPL 系と整合しないため取らない |

| 中核体験 | 録音の途中でも自分の声で歌を聴ける（即時試唱） |

| 合成 | WORLD ベース。ニューラルボコーダへの置き換えは採らない。F0 推定のみ SwiftF0 に差し替え（コーパス監査が前提） |

この制約から機械的に導かれる技術的帰結が3つある。いずれも一次情報で確認済みで、選択の余地がない。

- **[Fact] resampler は WORLD（BSD-3-Clause）ベースを自前ビルドする以外に選択肢がない。** 外部 `.exe` resampler（moresampler、UTAU 同梱 resampler.exe）は Windows 専用で、macOS / Linux では Wine を要し「単一のネイティブアプリケーション」と両立しない。
- **[Fact] Python / Conda ランタイムは配布物に含められない。** したがってアライナは、ネイティブ実装または ONNX 推論に落とせるものだけが候補になる。
- **[Fact] AGPL-3.0 を選んだことで、GUI 基盤のライセンス制約は解除された。** GPLv3 のコードを取り込めるため、Slint（GPLv3 オプション）、Qt（GPLv3）、Rubber Band Library（GPL）が候補に戻る。同時に **worldline の GPL-2.0-or-later も AGPL-3.0 に取り込めるため、`@spline` の自前実装は不要になった**（blocker B1 の解消）。
- **[Fact] Windows では WebView2 を固定バージョンで同梱でき、環境依存を排除できる。** 配布サイズは約180MB 増える。macOS の WKWebView は OS 同梱。Linux の WebKitGTK はディストロ依存が残るが、Flatpak の runtime に含めることで緩和できる。Linux は中核機能のみの第三対応環境という位置づけと整合する。
- **[Assumption] エディタの描画データはタイル化して raw bytes で受け渡す必要がある。** Tauri のフロントは WebView なので、Rust 側が持つ全解像度データから可視域のタイルだけを渡す設計になる。JSON シリアライズを通す経路は使えない。これにより1フレームあたりのデータ量は画面サイズで上限が決まり、プロジェクト規模に依存しなくなる。
- **撤回した基準**: 「起動時に外部プロセスまたはブラウザエンジンの初期化を待たない」（TR-PLT-03 の条件 h）は、実装スタックを Rust + Tauri に決めたため撤回する。これは自ら課した基準であり、製品要件ではなかった。ただし「起動から最初のフレーズ録音までの時間」は TR-PLT-17 の目標値として残す。

# 未解決の設計課題

**判断が必要な論点は残っていない。** 当初 blocker として挙げた10件のうち8件は決定によって解消し、残る2件はいずれも解決方針まで定まった作業として残っている。要件本文からの参照を保つため、解消したものも ID と経緯を残す。

## B5. 領域別メモリ上限の合計が、プロセス全体のピークメモリ上限を超えている

**[Fact]** platform は「多音階連続音・約3時間分の素材を持つプロジェクトを開いた状態でピークメモリ ≤ 1.5GB（8GB 搭載機で他アプリと共存）」と置く。一方、各領域が独立に確保しているのは:

| 領域 | 項目 | 上限 |
|---|---|---|
| align | アライメント処理に帰属する分 | 500MB |
| synth | 解析結果のメモリ LRU | 512MB |
| editor | 常駐メモリ（音声＋チャート画像） | 512MB |
| editor | undo 履歴 | 200MB |
| **合計** | | **1,724MB** |

platform 上限を 15% 超過しており、しかもここには **WebView プロセス**、GUI のレンダリング面、波形 min/max ミップマップ、SQLite、録音リングバッファ（1000ms 以上を常時保持）が一切含まれていない。**4つの上限は独立に決められ、一度も突き合わされていない。**

**実装スタックを Rust + Tauri にしたことで、この課題は悪化している。** Tauri のフロントは OS の WebView を別プロセスで持つため、その常駐分（一般に数百MB規模）が丸ごと予算に加わる。一方で GC ヒープの余裕を見る必要はなくなった。**予算の構成が変わったので、数値の積み直しが必要である。**

**要件化する内容**（上限の持ち方を「領域ごとの独立キャップ」から「単一のプロセス全体予算からの配分」に変える）:

1. 1,500MB を実行モードで分割する。**録音中**（editor 非表示）は synth LRU 512 + align + ランタイム、**編集中**（録音停止）は editor 512 + undo 200 + ランタイム。align と synth の LRU は editor が前面のとき 128MB へ縮退させる。モード遷移時に解放する契約を要件に書く。
2. align の 500MB は、実測（4秒テイク 13.5ms / 重み 1.25MB）から見て2桁過大なので **64MB 程度へ引き下げる**。これだけで 436MB が浮く。
4. **WebView プロセスの常駐分を実測して内訳表に入れる。** ここを空欄にしたまま他を詰めても意味がない。
3. 予算表に「プロセス全体 1,500MB の内訳表」を1枚追加し、各領域の数値をそこからの配分として再定義する。

## B6. 多音階規模のスペクトログラム画像だけで editor の常駐上限を使い切り、エントリ間移動 50ms が構造的に成立しない

**[Fact]** editor の解析パラメータは窓長 512・ホップ 2.29ms（44.1kHz で 101 サンプル）＝ 437 フレーム/秒、周波数ビン 257。

| 構成 | 実音声長 | チャート画像（1バイト/px） |
|---|---|---|
| 3音階連続音 | 約 3,120 秒 | 約 350MB |
| 8モーラ×5音階 | 約 5,200 秒 | 約 584MB |

RGBA で持てば 1.4GB / 2.3GB。**チャート画像だけで editor の常駐上限 512MB を単独で食い潰し、音声サンプルの分が残らない。** editor は「超えたら遠いチャンクを解放」と規定しているので破綻はしないが、**破綻しない代償として大半のエントリがチャート未計算状態になる。** すると適用されるのは editor 自身が定めた未計算時の 200ms 経路であり、platform の「エントリ間移動 ≤ 50ms（エントリ数 3000）」は満たせない。editor の rationale は「500エントリを1件50msなら合計25秒」だが、5,000エントリ × 200ms = **1,000秒（16.7分）** になり、上級モードが vLabeler の代替にならないという当該予算の目的そのものが達成できない。

加えて **[Fact]** editor のチャート事前計算スループット予算は「合計1800秒（30分）の音声を4コア以上で60秒以内」だが、対象プロジェクトの実音声は 3,120〜5,200 秒であり、スループット一定なら **104〜173秒**（予算の 1.7〜2.9 倍）かかる。

**要件化する内容**:

1. **チャートをメモリ常駐前提からディスクキャッシュ前提へ変える。**（Tauri を選んだことで、可視域のタイルだけを raw bytes で WebView へ渡す設計が必須になった。方向は一致しており、この項目はその具体化にあたる。） synth が既に持つ「合成済みフレーズのディスクキャッシュ 1GB/プロジェクト」と同じ構造で、スペクトログラム用のディスクキャッシュ予算（3音階で 350MB、5音階で 600MB）を新設し、メモリは可視域＋前後数エントリのウィンドウだけにする。ディスクからの mmap / 読み出しなら 50ms 予算に入る。
2. 予算表に欠けている「**スペクトログラムキャッシュのディスク使用量**」の行を追加する。この量はどの領域の予算表にも存在しない。
3. 事前計算スループット予算の分母を 1800 秒から、方式ごとの実音声長（単独音 約4分 / 連続音1音階 約26分 / 多音階3音階 約52分 / 多音階5音階 約87分）に置き換える。
4. 事前計算はエントリの走査順（録音リスト順）に先行させ、平均ではなく「**次の N エントリが常に計算済み**」を満たす形で優先度を付ける。

**なお、高頻度描画が GUI 基盤の選択肢を狭めるという懸念は成立しない。** **[Fact]** OpenUtau の `zoomInMel` は周波数軸の表示帯域を絞るトグル（FFT は 1024→2048 に増える）で時間軸拡大とは無関係、`UpdateMel` は WaveFile ロード時と `zoomInMel` 変更時にしか呼ばれず、ホップは `SamplingRate/400` = 2.5ms 固定。**OpenUtau は水平ズーム・スクロールで STFT を再計算していない。** これは TR-EDT-12 の反証ではなく最強の裏付けであり、rationale 側に置くべきものである。GUI への制約は「全画面ビットマップをソース矩形変換で 60fps 以上で再描画できる」のままでよい。最大拡大（0.227 ms/px、1000px で約 227ms ＝ 約 99 列を 1000px へ拡大）でもバイリニア補間の blit で足りる。**狭まるのは描画性能側ではなくメモリ側であり、そこが上記のとおり破綻している。**

## 解消した論点

以下は決定によって解消した。要件本文からの参照先として ID を残す。決定の内容は [product-vision.md](./product-vision.md) の Scope にある。

| ID | 何が問題だったか | 何で解消したか |
|---|---|---|
| **B1** | worldline の共有ライブラリが GPL-2.0-or-later で、許諾的ライセンスの製品に同梱できない。OpenUtau が MIT であることも、OpenUtau がバイナリを配布している事実も再配布根拠にならない | **ライセンスを AGPL-3.0 にした。** GPL-2.0-or-later は AGPL-3.0 に取り込めるため、`@spline` の自前実装は不要になった |
| **B2** | MFA 日本語音響モデルの「CC BY 4.0」は再配布の根拠にならない。学習コーパスに再配布禁止・非商用限定のものが含まれ、TR-ALN-05 と TR-ALN-31 が正面衝突していた | **MFA を落とし、Julius を本命にした。** Julius エンジンは修正 BSD 3条項で、音響モデルは HTK ascii / binhmm 形式。同梱される `.binhmm` へのライセンス適用が文面上明示されていない点は、**ブロッカーではなく気になる点として記録する**判断を採った |
| **B3** | 精度目標を支える学習済みモデルが存在せず、代替の自前学習もライセンスクリアな日本語音素境界データが無いため着手できない | **Julius で実装を進める判断を採った。** 精度が水準に届くかは実装中に自分の声で測る技術リスクとして残るが、判断としては決着している。TR-ALN-32 の参照データ作成を実装の前提作業として前倒しする |
| **B4** | 精度不足時に「もっと大きいモデルへ」という逃げ道が、CPU 時間と同梱サイズの両方で閉じている | **候補が軽量になったため緩和された。** Julius の HMM-GMM は小さく、F0 推定に採る SwiftF0 はパラメータ 95,842個。同梱サイズと CPU 時間には大きな余裕がある |
| **B7** | `.frq` を「録音時の成果物」と「書き出し時の成果物」のどちらにするかが未決で、後者なら予算が約50倍外れる | **録音時に作ると決めた。** 即時試唱のための F0 解析がどうせ走るので、その副産物として書き出す |
| **B8** | ミニ音源の作り方が正反対の2案で同時に確定しており、曲先行の最短経路（F02 / F03）全体がその上に乗ったまま未決 | **録音リストを並び替えると決めた。** 先頭から順に録ると早い段階で歌える曲が現れる順序にする。課題曲と録音リストを同時に設計する必要があり、**その設計作業自体は残っている** |
| **B9** | 方式選択画面（製品の最初の画面）が、反証された所要時間算出式の上に [Fact] として立っている | **選択肢の主軸を「手作業が必要かどうか」に変えた。** 単独音と CVVC の録音時間差は2分程度で時間では選択肢が並ばない一方、自動原音設定が全自動で完結する見込みがあるのは単独音だけで、そこが利用者にとっての実質的な違いになる。所要時間は併記するが従属的に扱う |
| **B10** | 録音直後のオフライン前処理を配布 WAV に反映するかが未決で、担当要件そのものが存在せず、TR-REC-37 / TR-PKG-39 と正面衝突していた | **試唱と配布に同じく適用すると決めた。** 本人が確認した音と手渡した音を一致させる。マスター（32bit float）は不変で保持し、前処理済みは再生成可能なキャッシュとして別層に置く |

# 領域別の技術要件

7領域。各領域は「中核要件（満たさなければ成立しない）」「その他の要件の要旨」「候補技術」「その領域の [Risk] と [Unknown]」で構成する。

> **実装スタック変更による失効の告知（重要）**
>
> 以下の領域別要件は **.NET + Avalonia + Microsoft Store を前提に書かれている。実装スタックは Rust + Tauri、配布は直接ダウンロード主経路に変更されたため、その前提に依存する記述は失効している。** 要件そのものの意図（何を満たすべきか）は有効なので破棄せず、以下の対応表で読み替える。
>
> **失効した記述**
>
> - **TR-PLT-03 の条件 (g)（MSIX 化して Store に提出できる）と (h)（起動時にブラウザエンジンの初期化を待たない）** — 撤回。(g) は Store 経路を取らないため、(h) は Tauri を選んだため。
> - **TR-PLT-12（Windows の主配布経路を Microsoft Store とする）** — 撤回。直接ダウンロードを主経路とし、Windows は WebView2 の固定バージョンを同梱する（配布サイズ +約180MB）。
> - **候補技術表の「Microsoft Store / MSIX」「.NET 8 / .NET 10」「Avalonia」「Compose Multiplatform」** — いずれも不採用。
> - **「Tauri / Electron / egui / iced / .NET MAUI は不適」という判定** — 撤回。判定根拠だった (c)(d)(h) のうち (h) は撤回され、(c)(d) は Rust なら FFI と WebGL 描画で満たせる。加えて **Tauri は日本語 IME と OS アクセシビリティ API への対応が最も確実**であり、アクセシビリティを既定要件とした判断と整合する。
> - **LGPL 部品と Store 配布の非両立に関する記述** — Store を取らないため前提が消えた。ただし libsoxr → libsamplerate の置換など、指摘された回避策自体は有効なので残す。
> - **配布サイズの見積もり（win-x64 で 33〜48MB 等）** — .NET self-contained を前提とした数値なので失効。WebView2 固定バージョンの同梱で構成が変わる。
>
> **候補技術の読み替え**
>
> | 失効した候補 | 用途 | Rust 側 | 判定 |
> |---|---|---|---|
> | .NET 8 / .NET 10 | 実行基盤 | Rust 1.95 / edition 2024 | 採用 |

>
> **新設が必要な要件**
>
> エディタの描画データを**タイル化して raw bytes で受け渡す**要件。Tauri のフロントは WebView なので、Rust 側が持つ全解像度データから可視域のタイルだけを渡す。JSON シリアライズを通す経路は使えない（custom protocol か IPC の raw チャネル）。これにより1フレームあたりのデータ量は画面サイズで上限が決まり、プロジェクト規模に依存しなくなる。TR-PLT-04 の「可視域のみ計算・可視域のみ描画」の具体化にあたる。

### その他の要件の要旨

TR-PLT-02 はリリース資産を win-x64 / osx-arm64 / osx-x64 / linux-x64 の4構成とし、macOS は universal2 ではなく別ビルドとする。TR-PLT-04 は波形・スペクトログラムをアプリ所有の単一描画面へ直接描き「可視域のみ計算・可視域のみ描画」を原則とする（B6 の帰結でディスクキャッシュ前提に修正が要る）。TR-PLT-08 / 09 は CP932 の読み書きと日本語 IME 入力を要求する。TR-PLT-15 は Linux の配布形態、TR-PLT-16 は自動更新、TR-PLT-17 は発見から着手までの段差の最小化、TR-PLT-18 はマイク権限の取得と拒否からの回復、TR-PLT-21 はプロセス構成、TR-PLT-24 はショートカット中心操作の OS 差の吸収を扱う。

**TR-PLT-10 は書き換えが必要。** **[Fact] OpenUtau.Core は公開レジストリに存在しない。** 「NuGet 依存として取り込む」という表現を削除し、取り得る形を「MIT ライセンス下でのソース同梱（vendoring / submodule、改変箇所と由来を明示）」「仕様参照＋自前実装」の2択として書く。上流追従は自動ではなく手動マージ運用になる前提でコストを見積もる。いずれの形でも共通の必須条件として「**生成した音源が OpenUtau の最新リリースで読み込めることを CI で検証する**」を残す。これが出力互換の唯一の実質的な保証である。粒度が合うかの確認（`VoicebankLoader` が oto.ini / character.txt / prefix.map を「書き出せる」か「読むだけ」か、phonemizer が録音リスト生成に転用できる形で音素列を返すか）は、要件を確定する前に実物のソースで済ませる。

## 2. 録音サブシステム（TR-REC-01〜40）

出口が UTAU である一点で設計がほぼ決まる。**[Fact]** OpenUtau の VoicebankErrorChecker は WAV が 44100 Hz / 16 bit / 1ch でなければエラーを出し、WAV ファイル名が NFD であることも、大文字小文字だけが違う重複も、alias の前後空白・全角空白もエラーとして報告する。**保存フォーマットとファイル名規則には交渉の余地がない。**

### この領域の [Risk] / [Unknown]

- **[Fact] 「RAW 要求と IAudioEffectsManager で OS 加工を外せる」と書いてはならない。** RAW は AUDCLNT_STREAMOPTIONS の定義上、APO・ドライバ・ハードウェアのエンドポイント固有な常時オン処理を除外しない。したがって**機材内蔵 DSP による AGC / NS は KOERU からは検知も無効化もできず、加工なしを保証する手段は存在しない。** **[Unknown]** 無効化の可否は RawProcessingSupported、ドライバのサポートモード、APO が IAudioSystemEffects3 を実装しているか、canSetState、および OS ビルドの積で決まり、成功率は不明で見積りに用いない。**列挙結果が空であることを「加工なし」の証拠として扱わない。** メタデータには「列挙結果が空」「列挙不能」「無効化成功」「無効化拒否」を区別して記録する。**最重要: アライメント精度の見積りを「加工されていない声」の前提に接続してはならない。** 既知の境界誤差の数値はクリーンなコーパスでの測定値であり、AGC・NS を通った信号での境界誤差は **[Unknown]** である。
- **[Fact] 校正とゲイン固定で破綻は防げない。** 校正の目的は「破綻の防止」ではなく「初期値の妥当化」に限定する。上限を -3 dBFS ではなく **-6 dBFS 程度に下げ**、校正発声を「そのプロジェクトで最も高い音高の全力発声」で行う（多音階では最高音高で校正）。32bit float マスターを持つ設計では 16bit の余裕は問題にならないため、ヘッドルームを優先する。**[Fact]** RAW 経路ではエンドポイントボリュームが効かない可能性があるため、ゲイン制御はハードウェアボリュームを持つデバイスに限定し、ソフトウェア実装のボリュームは「校正に使えない」として区別して記録する。API が読み書きできないデバイスでは校正が自動で成立しない。**[Risk]** リアルタイム品質判定がスコープ外である以上、破綻の検知はスコープ外ではなく**未解決の残存リスク**として明示的に残す。→ 少なくともフルスケール到達サンプル数については、**配布パッケージ生成の直前に集計して一度だけ提示する関門**を置く。これは収録中のリアルタイム判定ではないためスコープを侵さず、壊れた成果物が完成に到達する経路を塞げる唯一の安価な手当てである。
- **[Fact] 出力エンドポイントの種別判定ではガイド音の回り込みを構造的に排除できない。** FormFactor / TransportType はドライバの自己申告であり、UnknownFormFactor が正規値として存在する。判定結果は記録するが安全側の根拠として使わない。FormFactor が Headphones であってもヘッドホンが装着されている保証はない。**回り込みは録音側でしか確認できない。** → 「収録前に一度だけ、ガイドを鳴らしながら1秒キャプチャして、ガイドの既知信号との相関でリークの有無を確認する」セットアップ工程を追加する。これは TR-REC-17 と同じ性質の静的な経路検査であり、既知の再生信号との相関を使えば声質評価を一切含まずに判定できるため、スコープ外制約と衝突しない。**[Risk]** この検査を置かない場合、「全テイクにガイドが混入した音源が完成に到達しうる」ことを未解決リスクとして明示する。
- **[Fact] リサンプル品質の SNR / 帯域は、20ms 級の境界誤差予算の根拠にならない。** 誤差予算の項目から SNR / 帯域を根拠とする記述を外し、リサンプル品質は「エイリアシングと帯域の確保」の項目として独立させる。時間軸に対して意味のある唯一の条件は「**使用するリサンプラの群遅延をサンプル単位で既知とし、マスター上で補償済みであること**」であり、これを要件として書く。libsamplerate の 97dB / 97% は測定条件が公開されていないため confidence を Fact から Assumption に下げ、可能なら 48000→44100 の実測（スイープのエイリアシング測定と既知パルスの群遅延測定）を受け入れ基準に置き換える。**20ms 級の予算に本当に効くのはリサンプルではなく、上流の適応処理とテイクの時間軸完全性（TR-REC-07）である。**
- **[Unknown] macOS の AVCaptureDevice のマイクモード値が、AUHAL 経由の素の HAL キャプチャに反映されるかが不明。** 反映されない場合、Voice Isolation で加工されているのに standard と報告される可能性があり、TR-REC-11 の検知は空振りになる。実機での検証が必要。
- **[Unknown] プロジェクトディレクトリがクラウド同期フォルダに置かれた場合の扱いが未決。** SQLite の破損と、macOS 側で分解形のファイル名が持ち込まれる経路の両方のリスクがある。同期対象外への配置を強制するか、案内にとどめるかを決める必要がある。
- **[Unknown] ディスク枯渇時の書き込み失敗に対する要件がない。** TR-REC-21 がプロジェクト総容量 4GB 超過時の削除候補提示を持つのみで、3時間の収録中に OS のディスクが埋まって書き込みが失敗する経路（TR-REC-28 の `.part` 書き込み、TR-EDT-15 のディスクキャッシュ、TR-SYN-25 の解析キャッシュ）に対する検知・停止・保全の要件が存在しない。→ TR-REC-28 に「書き込み失敗と空き容量閾値を検知したら収録を停止し、確定済みテイクを保全し、原因と復帰手順を提示する」を追加する。**リアルタイム品質判定ではなくデータ完全性の破綻なので、スコープ外制約と衝突しない。**

### その他の要件の要旨

TR-RCL-03 は単独音のリストを1行あたり最大単位数の制約下で最小行数に詰めて生成する。TR-RCL-05 は CVVC を CV・VC・語尾の3種のエイリアスを同時に回収する行として生成する。TR-RCL-07 は生成行に読み上げ可能性の制約を課し行ごとの読み間違いリスクを評価する。TR-RCL-10 は所要時間パラメータをユーザーの実測から更新し残り時間表示に反映する。TR-RCL-12 は課題曲を「モーラ列 + MIDI ノート列 + 音域」のデータとして持ち権利上同梱可能なものだけを収録する（**Unknown**。B8 参照）。TR-RCL-13 は歌詞のモーラ分割と特殊モーラの正規化規則を1箇所に定義する。TR-RCL-14 は生の歌詞テキストの g2p 変換とユーザー修正。TR-RCL-17 は「あと何フレーズ録れば次の曲が歌えるか」を収録済み単位からの増分被覆として算出する。TR-RCL-22 は課題曲の音域と収録音高の整合判定。TR-RCL-25 は同一行の複数テイクの保持と採用テイク切り替えでカバレッジが変わらないこと。TR-RCL-26 は多音階のカバレッジを音高ごとに独立管理し進捗表示では音高を跨いだ最小値で扱う。TR-RCL-27 は録音リスト生成の決定性（同じプリセットとインベントリからは常に同一のリスト）。

## 4. 自動原音設定（強制アライメントと oto 推定、TR-ALN-01〜32）

## 5. 即時試唱と合成エンジン（TR-SYN-01〜34）

**[Fact] 試唱レイテンシは「押下後に何を計算するか」ではなく「録音直後に何を計算し終えているか」で決まる。** 周波数表（`.frq`）が無いと合成コアは音符ごとに pYIN を WAV 全長へ走らせる。周波数表を録音直後に生成しておけば F0 は読み出すだけになる。一方でスペクトル包絡と非周期性指標は約 1.6MB/秒（単独音1本 約8分で約 790MB）になり永続化できないため、これらは切り出し区間だけ都度計算し、フレーズ単位の合成済み波形をキャッシュする。

### この領域の [Risk] / [Unknown]

- **[Unknown] イヤホンマイク・家庭環境・通常の声量で録った素材が WORLD 系合成コアで嬉しい品質になるかは未検証で、この領域の全要件がその上に乗っている。** 劣化の機構も未特定（B10 に想定される3経路と、実測なしに断定しない旨を記載）。**この領域で最初にやる実測は前処理あり／なしの主観比較である。**
- **[Unknown] Harvest の RTF が未実測で、E2E 予算の中で最も外れやすい項である。** synth の予算は「4秒 WAV・F0 下限 55Hz で 1.0 秒」＝ RTF 0.25 だが、basis 自身が未実測と自認している。**この [Fact] の引き当てが誤っている**: WORLD が実時間で動くと報告されているのは **DIO + StoneMask** の経路であり、Harvest は品質を優先した別系統の推定器で、実時間では動かないという整理が上流の一般的な説明である（正確な倍率は一次資料で確認できず **[Unknown]**）。かつ F0 探索下限 55Hz は Harvest の候補帯域数を増やす方向に働く。連続音のテイクは4秒ではなく約6〜7秒（8モーラ×0.6秒＋前後マージン300ms×2＋プリロール500ms）なので、RTF 0.25 でも 1.5〜1.75秒、RTF 1.0 なら **6〜7秒**。後者では周波数表生成の1工程だけで「録音1件の前処理完了 5秒」の枠を単独で破る。→ **Harvest / DIO+StoneMask の RTF を、想定端末に相当する実機で下限 55Hz と話者音域確定後（下限 100Hz 前後）の両方について測る作業を、要件確定より前のベンチマーク項目として立てる。** 予算の basis から「WORLD は査読論文で実時間処理に足る速度と報告されている」という Harvest への引き当てを削除し **[Unknown]** と書く。
- **[Unknown] F0 下限 55Hz は CheapTrick の FFT 長を 2048 から 4096 に倍加させ、まさに初回試唱の瞬間にそれが起きる。** 予算表では「1音符あたりの合成 80ms」の条件が **FFT 長 2048**、「周波数表生成 1.0 秒」の条件が **F0 下限 55Hz** で、同じパイプラインの2つの予算が異なる FFT 長を前提にしている。実際の初回試唱は録音がまだ8件しかなく話者音域が確定していない時点なので**必ず 55Hz / FFT4096 側で走る。** → 音域確定を試唱まで待たず、入力レベル校正と最初の数テイクから F0 の粗い下限を推定して**初回試唱の前に**下限を引き上げる。単独音の1〜2テイクで下限を「推定最低音 − 3半音」に置けば、多くの話者で 71Hz 以上になり FFT 2048 に落ちる。予算表の両行に前提の FFT 長と F0 下限を明示的に併記する。
- **[Unknown] 「1音符 80ms」の係数自体が未実測である。** E2E 予算全体がこの1つの未実測係数に乗っている。**Harvest の RTF とあわせて、この2つが E2E 予算のうち唯一の未実測項目であり、測れば予算表は確定する。**
- **[Risk] 「録音品質のリアルタイム判定はスコープ外」と「試唱が中核体験」の組み合わせにより、音量不足・クリッピング・環境ノイズを含む素材でもそのまま試唱に出る。** 結果として試唱が事実上の品質判定の場になるが、TR-SYN-20 で評価軸を出さないため、ユーザーは「なんか変」と感じても原因が分からない。**原因を示さずに録り直しへ誘導する手段が要る。**
- **[Risk] 自動原音設定が試唱の前提工程になるため、自動アライメントが失敗した素材の扱いを決める必要がある。** 選択肢は (a) 試唱から除外して欠損扱い、(b) 粗い推定値で鳴らす、(c) 確信度が閾値を下回った項目だけ即時に確認を求める。(c) は UC-F04-02 と整合するが、**初回試唱の直前に確認作業を挟むことになり、報酬を先に届ける設計と衝突する。**
- **[Unknown] F0 推定手法（Harvest / DIO / pYIN / CREPE）を KOERU の録音条件で比較した実測が無い。** 周波数表は試唱と配布の両方に効くため、ここの精度が外れると影響範囲が広い。
- **[Unknown] 上位方式（連続音）で録った素材から下位方式（単独音）相当のエイリアスを切り出して試唱にも使うかが未決。** 使えば序盤のカバレッジが上がる。使わなければ連続音を選んだユーザーの初回試唱が遠くなる。
- **[Unknown] moresampler が生成する `.mrq` が音源ディレクトリに増える扱いが未決。** 同梱候補からは platform 制約で外れるが、「KOERU で録った音源を moresampler で鳴らす人がいる」ことは想定される。配布パッケージへ含めない／生成物として無視する、のいずれかを決める。
- **[Risk] 利用計測を実装しない方針の場合、TR-SYN-33 の目標レイテンシが実環境で達成できているかを知る経路が存在しない。**

## 6. 原音設定エディタ（setParam / vLabeler 同等、TR-EDT-01〜47）

**「同等」の定義。** **[Fact]** setParam と vLabeler が独立に到達した機能の**交差**は、5値のハンドル操作・波形とスペクトログラムの同軸表示・位置保持ドラッグの2モード・キーバインドの全面カスタマイズ・エイリアス一括操作・undo/redo。**setParam にしかない**のはゼロクロス吸着（パラメータ別に既定 on）・先行発声タイミング確認再生・合成試聴・数値テーブルの範囲編集で、vLabeler は後半2つを外部プラグインで補っている。**したがって「vLabeler と同等」だけを基準にすると、setParam ユーザ 70.9% が日常的に使う機能が落ちる。** **vLabeler にしかない**のは複数 oto.ini のモジュール管理と、絞り込みを移動に連動させる機構。**[Fact] どちらのツールも prefix.map を編集しない**（setParam のソースには「prefixMap に未対応」の注記がある）ため、多音階の接頭辞管理はエコシステムに空いており、方式を最初に選ばせる KOERU は自前で持つ必要がある。

### この領域の [Risk] / [Unknown]

- **[Risk] 「原音設定を自分でやらずに済む」と「録音品質のリアルタイム判定はスコープ外」が両立しない場面がある。** 音量不足・クリッピング・過大なノイズのある録音は自動推定の要確認スコアを確実に上げるが、原因が録音品質であることは編集画面からは分からない。**結果として通常モードは「境界がずれている」として提示し、ユーザは境界を動かして直そうとするが直らない。** 編集画面で「これは録り直したほうがよい」と言えるようにするには、録音品質の判定を編集フェーズに後付けで持ち込むことになる。**判定を持たないなら、通常モードは直せない問題を直させ続けることになる。**
- **[Risk] 下位方式書き出し時の写像（連続音の語頭を単独音として切り出す）を、エディタの一括編集として持つのか書き出し領域が持つのかが未決。** エディタが持つと、書き出し方式ごとに別の oto.ini が生まれ、TR-EDT-37 の「往復で何が失われるか」の設計が方式ごとに分岐する。
- **[Unknown] TR-EDT-20 のゼロクロス吸着で、setParam と同じ「ピッチマーク左側の右上がりゼロクロス」を実装するにはピッチマークの算出が必要。** F0 推定を自動推定領域から借りるのか、単純な「左方向の直近の立ち上がりゼロクロス」で代替するのかが未決。代替した場合、setParam と結果が一致しないことをユーザがどう受け取るか。

## 7. パッケージング・互換性・データ永続化（TR-PKG-01〜57）

**[Fact]** UTAU 音源パッケージの構成要素と落とし穴は、OpenUtau の Classic 名前空間（VoicebankLoader / VoicebankConfig / VoicebankErrorChecker / Frq / VoicebankInstaller / VoicebankPublisher、MIT）の実装から機械的に確定できる。character.txt が音源ルートの判定基準であり、解釈されるキーは 7 つに限られる。

**[Fact] 最大の実装上の罠**は、エイリアス重複が全 oto.ini 横断で Error になること、oto.ini の WAV 参照が NFD だと Error になること、小文字化衝突と大文字小文字不一致が開発機では再現せず配布先で初めて壊れること、そして **OpenUtau 自身のルート直下の大小一致検査が `chatacter.txt` と綴りを誤っていて character.txt を検査していない**ことである。

### 符号化は2層に分離して解く

**[Fact]** 「テキストを CP932 で書き、character.yaml に `text_file_encoding: shift_jis` を宣言すれば両対応になる」という単一の根拠に設計を乗せない。符号化の問題を**テキストの中身**と**ファイル名 / ZIP エントリ名**の2層に分ける。

- **ファイル名層は符号化問題を持ち込まないことで解く。** **内部（UUID ディレクトリ配下のマスターと DB）のファイル名を ASCII のみ（英数字・アンダースコア・ハイフン・ドット）に固定し、台帳との突き合わせは行 ID で行う。** これにより entryNameEncoding、EFS フラグ、NFD 混入、CP932 往復可能性、小文字化衝突、受け手側の展開ツールのロケール依存が内部からは一斉に消える。
- **日本語ファイル名は「配布パッケージ生成」と「外部ツール用に書き出す」の2つの出力時にのみ、package 領域が単独で所有する写像として生成する。** これにより CP932 往復・NFD・EFS・大小衝突のリスクを1箇所に閉じたまま、受け手と外部ツールが見る名前は慣習どおりになる（setParam / vLabeler でファイル名から行内容が読める。`.frq` の命名規約 `あ.wav → あ_wav.frq` も慣習どおりに保てる）。
- **テキストの中身の既定は CP932 とする。ただし根拠は「character.yaml で宣言するから」ではなく「OpenUtau の既定が shift_jis であり、classic 系ツールは CP932 しか想定していないから」である。** character.yaml の `text_file_encoding` は明示のために書くが、両対応の成立要件ではない。
- **プロファイルはテキスト符号化の2本（CP932 既定 / UTF-8）で足り、ZIP 側はプロファイルに依存しない。** entryNameEncoding に CP932 を渡す実装を残す場合、起動時のセルフテストで「CP932 で ZIP を書いて読み戻せること」を実測し、失敗したら ASCII 固定に縮退する。

### この領域の [Risk] / [Unknown]

- **[Risk] 音源名の自由入力と classic 互換（CP932）は両立しない場合がある。** 音源名は character.txt の name として配布物に現れるため、CP932 で表現できない文字（絵文字、簡体字、ハングル、結合ダイアクリティカル）を含む名前は classic 互換プロファイルで書き出せない。「仮名で始めて後から改名できる」（UC-F01-02）を成立させるには、表示名と配布名を分離してユーザーに配布名を別途決めさせるか、入力時点で文字集合を制限するかのどちらかが要る。**どちらも「名前で止まらない」という要件を削る。**

- **[Unknown] 利用規約テンプレートを何種類・どの粒度で同梱するかが未決。** 設問から生成する方式は決まるが、生成された文面の法的有効性を KOERU がどこまで表明するか（あるいは一切表明しないか）は決まっていない。

**押下時に前処理が全件完了していれば 0.4〜0.7s で収まる。ただしこの条件は初回試唱では原理的に成立しない。** TR-SYN-34 は「試唱押下時に未完了の項目があれば押下側で待ち合わせる」と定め、journey-map の【初めて歌う】は8フレーズを録り終えた直後に試唱する導線である。**最後の1件の前処理は押下の数秒前に始まったばかりで、必ず未完了である。**

**実際に起きること**: 最後の1件の前処理 4.6〜4.8s ＋ 押下後 0.4〜0.7s ＝ **約5〜5.5秒**。Harvest が実時間相当なら **約10〜12秒**。**[Fact]** journey-map の「数十秒の待ち時間のあと」の枠内であり、TR-SYN-33 の最悪 30 秒枠も破らない。**体験としては許容できる。破綻しているのは予算の定義であって体験ではない。**

**E2E 予算を縮める最も効く一手は、モデルの小型化でも並列化でもなく、align 枠 3.0s の実測への差し替えである。** これは実測（4秒テイクで 13.5ms、RTF 0.0034）に対して200倍以上の過大確保であり、TR-ALN-10 の元の 300ms へ詰めれば前処理は 4.6〜4.8s → **2.0〜2.2s** に落ち、押下後を足しても**約2.5秒**になる。

## 到着率の競合は起きない

**[Fact]** 単独音で KOERU 目標ペース 7.7s/行、連続音で 13.1s/行に対し、1件の前処理は 4.6〜4.8s。同時実行数を論理コアの 1/2（4コアで2）に絞ってもワーカ利用率は 35〜60% で、キューは単調増加しない。**崩れるのは別の3経路である。**

1. 押下時に必ず最後の1件が処理中（上記）。
2. **[Risk]** .NET の GC 停止時間による録音ドロップ。**「論理コア数の 1/2」制限はこれを一切防がない。** → TR-SYN-34 の GC 対策（録音入力パスでヒープ確保をしない、バッファのプール化、ワーカを別スレッドに置く、Server GC / 低遅延モードの検証）。
3. 全件再推定との三つ巴（下記）。

## 全件再推定の後始末に予算がない

**[Fact]** アライナ推論自体は3時間の音声に対し約36秒で済み、align の 10分予算に16倍の余裕がある。**問題は推論ではなく、その後始末が誰の予算にも入っていないことである。**

- 全件再推定は oto の5値を動かすので TR-SYN-26 により**該当する全フレーズのキャッシュが破棄される。** 合成済みフレーズのディスクキャッシュは 1GB / プロジェクトで、これを再構築するには曲全体の合成を RTF 0.16〜0.32 で回し直すことになる。**この工程を持つ予算行が存在しない。**
- 全件再推定は master WAV を全件読み直す。3,120秒 × 176.4kB/s = **550MB** のディスク読み出し。recording の書き込み帯域予算とは別の帯域を同じディスク上で要求するが、この競合は予算化されていない。
- TR-SYN-34 の並列度制限は録音直後の前処理に対する制約であって、**全件再推定が同じプールを使うのか別枠なのか、どちらが優先されるのかを定めた要件がない。** 多音階収録は4〜6セッションに分割される想定なので、セッションNの途中でプリセットを変えて全件再推定が走り、そのままセッションN+1の録音に入る、という並びは通常運用である。

**要件化する内容**: (a) **全件再推定を録音セッション中は開始しない**（トリガはセッション終了時または明示的な操作に限り、録音中に発火した場合はセッション終了までキューに積む）。これで競合はほぼ消える。(b) 予算表に「全件再推定後のキャッシュ再構築」の行を新設し、再構築を遅延・オンデマンドにする。(c) ワーカプールの優先度を明示する（TR-SYN-34）。

# 要件間の矛盾と、担当が抜けている領域

blocker として切り出したもの（B1〜B10）を除く、要件どうしの衝突と空白。**いずれも実装着手前に解消しないと、2つの領域が別々のものを作る。**

## 領域間の依存が宣言されておらず、同一のものが二重定義されている

261要件のうち、**領域を跨ぐ依存（`depends_on`）を宣言しているものは0件**である。その結果、同じアルゴリズムが2つの領域で別々に定義され、内容が食い違っている。

| 二重定義されているもの | 食い違い | 該当要件 |
|---|---|---|
| エイリアス解決のフォールバック順序 | **CVVC で順序が逆になっている。** 一方は VC を優先し、他方は CV を優先する。どちらで実装しても、もう一方の要件を満たさない | TR-RCL-20 / TR-SYN-12、TR-RCL-19、TR-RCL-06 |
| 通常モードで人に確認させる件数 | ALN 側と EDT 側で件数が食い違う。**単独音以外では「用語を出さない」方針と両立する保証がない** | TR-ALN-24 / TR-ALN-25 / TR-ALN-28 / TR-ALN-32、TR-EDT-02 / TR-EDT-05 / TR-EDT-06 / TR-EDT-07 / TR-EDT-45 |
| 下位方式への書き出し | **3領域でバラバラに定義され、oto の再導出を誰も担当していない。** 再切り出しが必要であることは訂正済みなのに、oto.ini だけで作る前提の要件が残っている | TR-RCL-21、TR-PKG-24 / TR-PKG-25（訂正で否定済み）、TR-ALN-13 / TR-ALN-16 / TR-ALN-18 / TR-ALN-19、TR-REC-38 |
| 「3時間の多音階連続音」の規模 | **領域ごとに3つの異なる数値で想定されており、同じプロジェクトを指していない。** 予算の突き合わせが成立しない | TR-RCL-09、PLT / EDT / PKG / REC の各予算 |

**[Risk]** 依存が宣言されていないため、片方の要件を直したときにもう片方が壊れることを検出できない。要件 ID 間の依存関係を明示することが、他のどの修正よりも先に来る。

## ファイル名の符号化方針が2領域で両立しない

RCL は日本語のファイル名を前提とし、PKG は ASCII 固定を要求している。**PKG 側の訂正は6要件を一括で解く代わりに、TR-RCL-08 と TR-RCL-18 を壊す。** どちらかを選ぶ必要がある。

| 選択肢 | 解ける | 壊れる |
|---|---|---|
| 日本語ファイル名を維持 | TR-RCL-08、TR-RCL-18 | CP932 表現可能性、macOS の NFD 正規化、大文字小文字だけが違う重複の回避 |
| ASCII 固定 | TR-PKG-11 / 14 / 39 / 45、TR-EDT-42 | TR-RCL-08、TR-RCL-18。**既存の UTAU 音源の慣例からも外れる** |

## 訂正済みなのに要件として残っているもの

敵対的検証で反証されたが、要件表からの削除が済んでいないもの。**残しておくと実装者が誤った前提で作る。**

- **TR-PKG-24 / TR-PKG-25** — 「oto.ini だけで下位方式パッケージを作れる」。再切り出しが必要（→ B に関連）
- **TR-PLT-10** — 「OpenUtau.Core を NuGet 依存として取り込む」。**[Fact]** 公開レジストリに存在しない。ソース同梱か自前実装の2択に書き換える
- **TR-ALN-13 / TR-ALN-16 / TR-ALN-17** — 「オーバーラップと子音部は規約値なので機械的に算出でき、確信度提示の対象外にできる」。対象外にできない
- **TR-ALN-03 の性能根拠** — snfa 系の小型 CTC アライナ自前移植で単独音の先行発声誤差 10ms 以内 90% に届く、という前提
- **TR-ALN-10** — 1テイクあたり 300ms 以内でアライメントと oto 推定を完了する予算

## ライセンスによって、既に選択肢が絞られている箇所

技術的な比較の前に、ライセンスだけで候補が落ちているもの。**比較検討の余地があると誤解しないための記録。**

| 論点 | 結論 |
|---|---|
| GUI 基盤 | **ライセンス条件だけで Avalonia と Compose Multiplatform の2択に確定する。** Qt / Slint / JUCE は検討対象に戻せない |
| LGPL 部品（alsa-lib、libsoxr） | **Microsoft Store（MSIX）を主配布経路にする TR-PLT-12 と両立しない。動的リンクにしても解決しない。** LGPL-2.1 の6節が要求する「利用者による差し替えと再リンク」が MSIX では成立しない |
| 文字コード判定（UTF.Unknown / uchardet） | MPL-1.1 が TR-PLT-22 の台帳ルールと字面で衝突する。**自前実装で両方落とせる。** UTAU 音源は CP932 と UTF-8 の2択なので汎用判定器は不要 |
| Unknown ライセンス部品（moresampler / setParam / resampler.exe） | **「調査中」ではなく「全権利留保」として扱う。** 逆コンパイル禁止の線を明示する |
| 日本語音響モデル | **[Unknown]** Julius segmentation-kit の License.md は対象を "the Software" と定義するだけで、同梱の `.binhmm` モデルファイルを明示的に含んでいない。学習コーパスの出所も未確認。**MFA を落とすとこれが唯一の権利クリアな候補になるため、根拠の薄さがそのままリスクになる**（→ B2、B3） |

## どの領域も担当していない技術要件

7領域のいずれにも要件が存在しないもの。**製品として出すには必要だが、現在の要件セットには空白として存在する。**

| 抜けている領域 | 内容 |
|---|---|
| UI の言語とローカライズ | KOERU 自身の UI 言語。日本語のみか、英語も持つか。UTAU 文化圏は日本語中心だが、OpenUtau・vLabeler・RecStar はいずれも多言語対応している |
| アクセシビリティ | スクリーンリーダー対応、キーボードのみでの操作完結、コントラスト。**ショートカット中心の設計はキーボード操作と親和的なので、要件化のコストは低い** |
| ディスク枯渇時の書き込み失敗 | 録音中・書き出し中にディスクが埋まった場合の挙動。**録音データの保護が絡むため後付けが難しい** |
| クラッシュ時の録音データ保護 | 3時間の多音階連続音の途中でプロセスが落ちた場合。予期しない終了からの復帰 |
| マイク切断・デバイス変更 | 録音中にデバイスが消えた場合の挙動。TR-PLT-05 がデバイス抜き差し検知を要求しているが、検知後の扱いが未定義 |
| 利用計測（A / B / C の未決） | **未決のまま TR-PKG-54 / 55 / 56 を宙吊りにしている。** 他領域の要件が「計測できる前提」で書かれている箇所があり、選択によっては成立しない |

**[Risk]** 上の6件は、いずれも「後から足せる」ように見えて、実際には録音データの扱いや配布形態に触るため後付けコストが高い。特にディスク枯渇とクラッシュ保護は、録音という「やり直しが高い操作」を扱う製品では中核に近い。

## 技術判断として新たに必要になった論点

### 1. worldline の GPL をどう扱うか（→ B1）

| 選択肢 | 帰結 |
|---|---|
| KOERU 自体を GPL で公開する | 配布は成立する。**ビジョンの「本人が所有し持ち運べる」とも整合しやすい。** ただしクローズドソース前提の事業判断は取れなくなる |
| 別の resampler を使う / 自前実装する | ライセンスは解ける。**WORLD 本体のライセンス確認と、合成品質の再評価が必要になる** |
| 別プロセス起動にして回避を試みる | **[Risk]** GPL の解釈として安全とは言えない。B1 は「OpenUtau がバイナリを配布している事実は KOERU の再配布根拠にならない」と明確に述べている |

### 2. アライナと日本語モデルをどうするか（→ B2、B3）

| 選択肢 | 帰結 |
|---|---|
| snfa 系 | **権利の系譜が3段すべて明示されており、台帳を単独で満たせる唯一の候補。** ただし重みは話声学習で、歌声・持続母音は未評価。**[Unknown]** 精度が実測されていない |
| Julius segmentation-kit | 日本語で実績があるが、**[Unknown]** モデルファイルへの MIT 適用と学習コーパスの出所が未確認。書面での確認が必要 |
| 自前学習 | **ライセンスクリアな日本語音素境界データが存在しないため、現状では着手できない**（→ B3） |

**[Risk]** この3つがすべて閉じた場合、「原音設定を自分でやらずに済む」という確定方針が単独音でも成立しなくなる。その場合に何を製品として出すのかは、技術判断ではなくプロダクト判断になる。

### 3. ミニ音源の設計（→ B8）

**正反対の2案が同時に確定した状態にある。** 曲先行の最短経路（F02 / F03）全体がこの上に乗っている。**録音リストと課題曲を同時に設計しないと、「先頭8項目だけで曲として成立する」は成立しない。** 五十音順のような自然な順序では成立しない。

### 4. `.frq` をいつ作るか（→ B7）

| 選択肢 | 帰結 |
|---|---|
| 録音時の成果物 | 録音1件ごとの前処理予算に載る。**ただし CPU の実質的な律速は WORLD Harvest であり、その RTF が未実測**（→ 性能予算） |
| 書き出し時の成果物 | **パッケージング予算が約50倍外れる。** 3秒の想定に対して実際は数分規模になる |

### 5. ファイル名の符号化方針

日本語ファイル名か ASCII 固定か。上の「要件間の矛盾」に選択肢と帰結を記載した。**既存の UTAU 音源の慣例は日本語ファイル名側にある。**

### 6. 録音直後のオフライン前処理を配布 WAV に反映するか（→ B10）

**担当要件そのものが存在せず、TR-REC-37 と TR-PKG-39 が正面衝突している。** 反映するなら「録音したまま」ではなくなり、反映しないなら前処理の成果が試唱にしか効かない。

### 7. 配布経路と対応 OS の保証水準

Microsoft Store（MSIX）を主経路にすると LGPL 部品が使えない。直接ダウンロードを同格の第一経路にする方針は要件に入っているが、**LGPL 部品を落とすか、Store を落とすかの判断は未了。** Linux の保証水準（中核機能のみ）も、配布形態と合わせて未確定。

### 8. 抜けている6領域を初期スコープに入れるか

UI の言語とローカライズ、アクセシビリティ、ディスク枯渇、クラッシュ時の録音データ保護、マイク切断からの回復、利用計測。**このうちディスク枯渇とクラッシュ保護は、録音という「やり直しが高い操作」を扱うため、後付けコストが特に高い。**
