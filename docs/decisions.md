## 2026-08-26

ペルソナ・セグメント整理（Stage 1）の Human Decision Gates に対する回答として決定した4件。

### D1. 検証フェーズを置かない

**決定**: プロトタイプは作らず、最初から本番として実装する。ユーザー検証・技術検証のフェーズを設けない。

**影響**: As-Is / To-Be JM とペルソナで **[Risk]** として挙げた以下は、検証されないまま実装の前提として持ち込まれる。

| Risk | 判明するタイミング |
|---|---|
| 自分の声が歌うのを聴くのが、本人にとって嬉しい体験か | 公開後 |
| イヤホンマイク・小声・生活音ありの条件で、聴いて嬉しい歌になるか | 公開後 |
| 方式非依存の中間表現が技術的に成立するか | 実装中に判明する |
| 既存制作者が RecStar + vLabeler から移行するか | 公開後 |

**見直しのトリガー**: 実装中に方式非依存の中間表現が成立しないと分かった場合、[product-vision.md](./product-vision.md) の How it's different と JM の To-Be 後半を書き直す必要がある。

### D2. 既定値は「プロジェクト作成」。オンボーディングで補う

**決定**: 起動直後の画面はプロジェクト作成。そのうえでオンボーディングを用意し、「あとで決める」モードへの導線が新規制作者にも分かるようにする。

**根拠**: 入口の構造は既存制作者（ハル）に合わせ、案内は新規制作者（ミナ）に合わせる。Primary をどちらか一方に倒さない。

**未解決の実装課題**: プロジェクト作成が最初に来ると、新規制作者は**まだ一度も自分の声を聞いていない段階で「音源の名前」を決める**ことになる。名前はキャラクター名でもあるため、技術的な設定ではなく創作上の決断になる。仮名で始められるか、あとから変えられるか、といった逃げ道の設計はオンボーディング設計で扱う。

**見直しのトリガー**: 新規制作者がプロジェクト作成画面で離脱していると分かった場合。

### D3. 非公開のまま完成できる状態を、正規ルートとして残す

**決定**: 手渡し（Made to be shared）を既定にしつつ、誰にも渡さずに完成できる状態を正規の完成形として扱う。

**根拠**: 調査で「恥ずかしい・自信がない」が 22.2%（n=63）。ただし「渡したくない」と「渡し方が分からない」は切り分けられていない **[Unknown]**。「渡したくない」の相当部分は「今は渡す自信がない」であり、時間とともに動く可能性がある **[Assumption]**。最初から締め出すと戻ってこられない。

**設計上の含意**: 「誰かに使われて、初めて完成する」は**思想として掲げるが、未完成の判定基準としては見せない**。完成の定義が2つになるため、進捗表現はそれを許容する形にする。

**見直しのトリガー**: 非公開完成の利用が極端に少ない、または逆に大半を占める場合。

### D4. 手渡しの実装範囲は「作る側に閉じる」

**決定**: 配布パッケージ（ZIP）の生成までを製品範囲とする。配布の場・音源の発見機能は持たない。

**根拠**: スコープが小さく、UTAU の分散型配布文化を壊さない。規約・権利・モデレーションを背負わずに済む。

**引き受けるリスク**: **[Risk]** 手渡しの先が製品の外にあるため、Made to be shared は製品機能としてはパッケージ生成までしか実装されない。「歌わせる側」（S3 / ペルソナ ユウ）に届く手段は製品内に存在しない。

**見直しのトリガー**: 現役制作者が「配布先が KOERU 内にあれば使う」と表明した場合。または、生成したパッケージが実際にどこにも配布されていないと分かった場合。

- **オンボーディングの具体設計** — D2 の逃げ道（仮名・改名）と、「あとで決める」導線の見せ方
